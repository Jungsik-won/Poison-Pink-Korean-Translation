# STATUS DB 구조 검증과 다음 주입 단계

검수일 2026-09-15. 원본 `SLPS_258.54`의 로더를 기준으로 확인했다.
파서: `tools/status_db_codec.py`. 재현: `python3 tools/status_db_audit.py`.
결과: `reports/status_db_audit.json`. 로더 바이트 증거: `build/db_audit/elf_evidence.json`.

## 1. 이번에 통과한 범위

세 파일 **85,016바이트 전체**, **13개 표 / 1,689개 레코드**를 순서대로 파싱하고 원본과 완전히 같게 재직렬화했다.
NUL 문자열 필드는 빈 필드 포함 1,941개, 비어 있지 않은 필드 1,388개다. 번역 대상 수나 고유 문장 수는 아니다.
모든 문자열의 엄격한 CP932 디코딩이 성공했다. 출력용 폰트에서 같은 의미의 글리프가 나오는지는 별도 검수한다.

| 파일 | 순서대로 읽는 표의 레코드 수 | 총 레코드 | 파일 크기 |
| --- | --- | ---: | ---: |
| PPITEM.dat | 150 / 46 / 59 / 21 / 119 | 395 | 12,918 |
| PPSKILL.dat | 194 | 194 | 23,969 |
| PPPARAM.dat | 271 / 251 / 265 / 25 / 42 / 102 / 144 | 1,100 | 48,129 |

각 표는 자체 `u16 count`로 시작한다. 첫 헤더는 첫 표의 개수다.
표마다 ID 공간이 다르다. 예를 들어 아이템의 앞 네 표는 각각 ID 1부터 시작한다.
PPPARAM 첫 표는 271행이지만 ID 범위는 1~444로 불연속이다. ID 바이트 검색으로 행을 복원하지 않는다.
고정 표 두 개(PPITEM 표 4, PPPARAM 표 3)는 행 위치를 사용하며 첫 2바이트를 ID로 해석하지 않는다.

## 2. 파일 레이아웃

`B=u8`, `H=u16 LE`, `I=u32 LE`, `Z=NUL로 끝나는 바이트 문자열`.
숫자는 부호 해석으로 원본을 바꾸지 않도록 unsigned로 저장한다. 실제 부호·게임상 의미는 추가 해석 대상이다.
아래 오프셋은 각 DAT 멤버 안의 위치이며 끝 위치는 제외한다. 표 번호는 0부터 시작한다.
각 범위에는 2바이트 count도 포함된다. 임의 정렬·0 패딩 건너뛰기·ID 검색은 없다.

### PPITEM

| 표 | 범위 | 행 포맷 | 로더 VA |
| --- | --- | --- | --- |
| 0 | 0x0000–0x165a | H ID, 2B, Z 이름, 21B 수치, Z 설명 | 0x275118 |
| 1 | 0x165a–0x1e22 | H ID, B, Z 이름, 28B 수치, Z 설명 | 0x275550 |
| 2 | 0x1e22–0x2bf0 | H ID, B, Z 이름, 45B 수치, Z 설명 | 0x2758b8 |
| 3 | 0x2bf0–0x2faa | H ID, B, Z 이름, 8B 수치, Z 설명 | 0x275ba0 |
| 4 | 0x2faa–0x3276 | BBHH (6B) | 0x275e08 |

수치 영역의 실제 필드 너비:

- 표 0: `4B + 6H + 3B + H = 21B`. 로더의 6회 스탯 루프는 인덱스 0, 5에서 입력을 읽지 않아 실제로 4H만 소비한다.
- 표 1: `3B + 7H + B + 5H = 28B`. 같은 방식의 스탯 루프와 후속 참조 값이 있다.
- 표 2: `3B + 21H = 45B`.
- 표 3: `B H B H H = 8B`.

이름 표본상 앞 네 표는 각각 무기·방어구·장신구류·소모품에 해당하는 것으로 보인다. 세부 분류는 추론이다.
앞 세 표의 설명 255개는 모두 빈 문자열이다. 표 3의 설명 21개는 비어 있지 않다.
빈 설명을 번역 대상으로 자동 채우지 않는다.

### PPSKILL

단일 표 `0x0000–0x5da1`: `H ID, H, H, Z 이름, 66B 수치, Z 설명`.
66바이트는 이름 종결 NUL **바로 다음 바이트부터** 센다.
필드 너비는 `3B + 5H + 8B + 19H + B + 3H`이다.

이름 NUL의 위치를 T라고 할 때:

- T+1..T+21: 초기 플래그·수치. T+15, T+19는 로더에서 소비 범위에는 포함되지만 읽지 않는다.
- T+22부터 2개, 11개, 6개의 2바이트 셀을 읽는다. 게임은 각 셀의 낮은 바이트만 메모리에 복사한다.
- 이후 `B+3H`, 다음에 설명 문자열이 온다.

파서는 읽지 않는 바이트와 버려지는 상위 바이트도 모두 보존한다.
첫 스킬은 이름 `パルフランマ`, 설명 `火属性：単体攻撃魔法\n射程：３↑３↓３`으로 정확히 분리된다.
기존 JSON의 9개 깨진 행은 새 구조 파서의 결과에서 발생하지 않았다.

### PPPARAM

| 표 | 범위 | 행 포맷 | 로더 VA |
| --- | --- | --- | --- |
| 0 | 0x0000–0x4bfd | H ID, H, Z 이름, 56B 수치 | 0x26c2e0 → 0x26c3e0 |
| 1 | 0x4bfd–0x717d | H ID, (Z 이름 + 10B 수치) × 2, 8B 수치 | 0x26ca18 |
| 2 | 0x717d–0x953a | H ID, B 개수 N, (BBHH) × N | 0x26ccd0 |
| 3 | 0x953a–0x982a | 18B + 6H (30B) | 0x26cef0 |
| 4 | 0x982a–0x9c16 | H ID, (B + Z 이름) × 3 | 0x26d110 |
| 5 | 0x9c16–0xb65f | H ID, HIIHBHH, Z 설명 | 0x26d2c8 |
| 6 | 0xb65f–0xbc01 | H ID, 4H (10B) | 0x26d568 |

표 0의 56B: `6B + 6H + 2B + H + 2B + 3H + 3H + (BH)×6 + H`.
표 1의 각 10B: `BBHHHH`, 후행 8B는 `4H`다.
표 2는 가변 개수지만 메모리 레코드 0x5e, 엔트리 시작 +4, 간격 6이므로 N≤15를 검사한다.
표 3은 메모리 600B에 24B씩 저장하므로 count≤25를 검사한다. 파일의 30B와 메모리의 24B를 혼동하지 않는다.

표 1에는 `ツメ`, `かみつき` 등 공격 이름으로 보이는 문자열이 있다.
표 4에는 `漆黒の魔姫` 등 칭호로 보이는 문자열이 있다. 둘 다 게임상 역할은 화면/호출처 검수 대상이다.
설명 문자열은 **별도 표 5의 ID 26~127, 102행**에 존재한다(비어 있지 않은 설명 101개).
따라서 과거의 “PPPARAM 128~271번이 도감 설명” 구획은 폐기한다. 설명의 도감 화면 연결은 별도 검증한다.

## 3. ELF 근거와 문자열 한도

ELF LOAD: file offset 0x1000 → VA 0x100000. 변환 `file_offset = VA - 0xff000`.

- PPITEM 진입 `0x2746d8`: `/status/PPITEM.dat`를 읽고 위 5개 로더를 순서대로 호출한다.
- PPSKILL 진입 `0x276a98`: `/status/PPSKILL.dat`를 읽고 로더 `0x276af0`를 호출한다.
- PPPARAM 진입 `0x26bcd8`: `/status/PPPARAM.dat`를 읽고 위 7개 로더를 호출한다.
- 각 다음 로더의 a1은 이전 로더가 반환한 v0, 즉 소비 후 파일 포인터다.
- `0x358900`은 NUL까지 복사한다. 스칼라 경로 `0x3589f0`은 lbu→sb 후 0까지 반복한다.
- `0x3591d8`은 문자열 길이를 센다. `0x3592ec` 경로에서 NUL 위치와 시작 주소의 차이를 반환한다.

문자열은 파일에서 가변 길이여도 메모리에서는 고정 공간에 복사된다.
다음 한도는 **NUL을 제외한 바이트 수의 보수적 상한**이며 실제 UI 폭 허용치가 아니다.

| 위치 | 이름 상한 | 설명 상한 |
| --- | ---: | ---: |
| PPITEM 표 0~3 | 18B | 127B |
| PPSKILL | 16B | 127B |
| PPPARAM 표 0 | 18B | 없음 |
| PPPARAM 표 1 이름 2개 | 각각 20B | 없음 |
| PPPARAM 표 4 이름 3개 | 각각 18B | 없음 |
| PPPARAM 표 5 | 없음 | 255B |

근거: 아이템 이름은 메모리 +3에서 시작하고 +0x16부터 수치가 사용된다.
스킬 이름은 +6, 다음 비트 필드는 +0x16의 상위 바이트(+0x17)부터 사용한다.
PPPARAM 표 0은 이름 +4, 다음 필드가 +0x17부터 사용한다.
표 1은 각 이름 시작을 S라 할 때 S+0x15부터 비트 필드가 사용된다.
표 4는 이름 앞 태그 1B를 포함한 슬롯 간격이 0x14다.
아이템/스킬 설명은 메모리 레코드 끝까지 0x80B, PPPARAM 표 5 설명은 0x100B다.

이 한도를 넘는 한국어 이름은 우선 의미를 유지하며 줄인다. 더 긴 이름이 필요하면 버퍼 확대와 모든 참조처를 별도 분석해야 한다.

## 4. 도구·검증 계약

- `parse(data, kind)`: count, 모든 필드, 행 경계, ID 중복, 버퍼 한도, 정확한 EOF를 검사한다.
- `serialize(model)`: 명시한 스키마 순서로 수치와 문자열 바이트를 다시 쓴다. 원본 파일을 통째로 되돌려 주는 방식이 아니다.
- 텍스트 값은 raw bytes다. CP932에는 같은 Unicode 문자에 대응하는 코드가 여러 개 있어 디코딩 후 재인코딩하면 원본 바이트가 달라질 수 있다.
- `replace_text`: `(표 번호, 행 순번, 필드명)` + 원본 파일 SHA-256 + 원문 바이트로 위치를 고정한다. ID만으로 수정하지 않는다.
- 수정은 문자열만 허용하며 수치 필드와 count/ID의 불변, 미수정 문자열 불변을 재파싱으로 검사한다.
- `status_db_audit.py`는 STATUS.HED/DAT와 ELF를 기존 source.lock에 대조한다.
- 검사용 필드 JSON·원본 멤버 사본·로더 raw bytes·실험 DAT는 `build/db_audit/`에 생성한다. 재실행 시 이 검사용 산출물을 갱신한다.
- 빈 문자열, 원래 길이, 각 버퍼 상한 길이로 모든 문자열 필드를 바꾸는 **9개 오프라인 ASCII 실험**이 수치 필드 불변·EOF 검사를 통과했다.
- 별도 테스트는 잘린 입력, 뒤에 붙은 바이트, 잘못된 count, 중복 ID, NUL 삽입, 인코딩 오류, 길이 초과, 원본 불일치와 CP932 별칭 바이트 보존을 검사한다.

통합 검수에서 원본 lock 일치와 기존 RTB 후보 해시 연결도 유지됨을 확인했다.
기존 테스트 33개와 신규 DB 테스트 9개, 총 **42개 통과**. 재현 명령:

```sh
PYTHONPATH=tools python3 -m unittest test_localization_pipeline test_iso_font_stage test_korean_sentence_probe test_rtb_codec test_tutorial_slice test_status_db_codec
python3 tools/status_db_audit.py
python3 tools/localization_pipeline.py audit
```

## 5. 다음 파이프라인

아래는 DB 구조 검수 직후 정한 순서다. 후속 작업에서 아이템 5개·스킬 5개의 주입과 16개 문자열 표시, 바람 공격·약초·회복 마법 사용 및 저장/로드를 확인했다. 최신 결과와 남은 QA037 범위는 [아이템·스킬 표본 실행 기록](STATUS_SLICE.md)을 따른다.

1. 튜토리얼/본편 첫 출격의 장비·소모품·스킬 화면에서 확인 가능한 **아이템 5개·스킬 5개**를 고른다. 표/ID/행/필드/원문 해시와 화면 위치를 검토 목록에 기록한다.
2. 용어를 맞춘 한국어 이름·설명과 의미를 유지한 축약안을 작성한다. 원문이 빈 설명은 자동 생성하지 않는다.
3. 실제 사용할 한글을 수집해 기존 슬롯 매핑과 합친다. NFC·게임 인코딩·누락 글리프·위 바이트 상한을 검사한다.
4. 해당 표본만 `replace_text`로 주입한다. 모든 수치 및 미수정 문자열이 보존됐는지 검사한다.
5. STATUS 멤버 크기와 다음 파일까지 패딩을 확인해 HED/DAT를 staging한다. 여유가 부족하면 검증된 재배치 경로를 별도로 준비한다. SYSTEM 폰트와 ISO도 같은 빌드에 묶는다.
6. Software 렌더러에서 이름·설명·선택·사용/장비·소비량·효과·다음 화면·저장/로드를 원본과 비교한다. 최대 폭 문자열도 캡처한다.
7. 실제 한글 화면과 기능 검증을 통과한 범위만 P4 완료 항목에 추가한다.

현재 `db_lossless_roundtrip=true`는 구조·무변경 왕복의 통과를 뜻한다.
이 플래그 자체는 DB 번역 주입의 실행 검증을 뜻하지 않는다. 후속 표본의 실행 검증과 UI 폭은 위 별도 기록에 있으며, 수치 필드 의미/참조 전체 해석과 배포 준비는 아직 완료하지 않았다.
